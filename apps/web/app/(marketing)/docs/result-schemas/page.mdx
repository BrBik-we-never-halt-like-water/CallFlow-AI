# Result schemas

Every call returns a schema-validated object. Not a transcript you have to read, and
not a summary you have to trust - a set of fields you defined, with the types you
asked for.

## Two fields you always get

| Field       | Type   | Meaning                               |
| ----------- | ------ | ------------------------------------- |
| `outcome`   | string | How the call ended, in a word or two. |
| `sentiment` | enum   | `positive`, `neutral`, or `negative`. |

`sentiment` is what makes a call log useful. It is the difference between two rows
that both say `completed` and two rows where one is jade and one is flare.

## Your own fields

Add fields to an agent, in the **Fields to collect** editor. Each one needs a key, a
type, a description, and a decision about whether it is required.

The description is not documentation - it is the instruction the extraction uses to
decide what belongs in that field. `"party_size"` with the description "number of
people travelling, including children" behaves differently from the same key with no
description at all. Write them as if explaining to a colleague who will fill the form
in for you.

The editor offers five types. Four of them travel to the service as themselves:

| Type      | Comes back as   | Use it for                           |
| --------- | --------------- | ------------------------------------ |
| `string`  | text            | Anything in the contact's own words. |
| `number`  | numeric         | Counts, durations, amounts.          |
| `integer` | a whole number  | Counts that cannot be fractional.    |
| `boolean` | true / false    | A yes-or-no fact.                    |

**Date** and **Choice** are the other two. Both are sent as `string`, with their
constraint folded into the description - "one of: onsite, hybrid, remote_only" is what
the engine actually reads when it decides what belongs in the field, so the constraint
still does its work while the transport type stays one the service validates.

Prefer **Choice** over plain text wherever the answers really are a fixed set. A free
text field for location fit will come back as "hybrid", "Hybrid", "2 days a week", and
"flexible" across four calls; a listed set of options comes back as one of your four
values far more often, and can be filtered.

## A missing field is missing, not invented

A field the contact never mentioned comes back null rather than invented. That is
deliberate, and it is why the results are trustworthy: an extraction that fills every
field on every call is guessing on some of them.

Marking a field **required** does not change that. It does not force the agent to
produce a value it does not have - it says the value matters. Two things follow. The
agent is told which fields are required, so its conversational priority matches yours.
And a call that connected and still ended without one is escalated rather than
auto-closed, with the missing fields named in the reason - see
[Triage rules](/docs/triage-rules).

So the rule of thumb is: required means "a person should chase this if the call did
not get it", not "invent it".

## Extraction happens during the call

The structured result is produced by the calling engine as the conversation happens,
against the schema you supplied. CallFlow does not parse transcripts afterwards.

That matters for two reasons. The obvious one is accuracy - extraction with the
conversation in hand beats extraction from a text dump of it. The less obvious one is
that a field the schema asked for and the contact did not answer can prompt the agent
to ask again, in the same call, which no post-hoc parser can do.

## Example

An agent qualifying leads, returning six fields:

```json
{
  "type": "object",
  "properties": {
    "outcome": { "type": "string" },
    "sentiment": {
      "type": "string",
      "enum": ["positive", "neutral", "negative"]
    },
    "problem": {
      "type": "string",
      "description": "The problem that prompted the enquiry, in the lead's words."
    },
    "volume": {
      "type": "string",
      "description": "Rough scale - seats, users, calls, or units."
    },
    "timeline": {
      "type": "string",
      "description": "When they are looking to decide."
    },
    "qualified": {
      "type": "boolean",
      "description": "True if the lead is worth a rep's time."
    }
  },
  "required": ["outcome", "sentiment"]
}
```

## Changing a schema later

Editing an agent's fields does not rewrite results that already exist. Old runs keep
the shape they were recorded with, so a report you built last month still works.

An agent is shared infrastructure - everyone in the organisation reads the same one -
so if you need a clean break, build a second agent rather than editing the one other
people's runs depend on. The runs stay separated and you can compare the two.
