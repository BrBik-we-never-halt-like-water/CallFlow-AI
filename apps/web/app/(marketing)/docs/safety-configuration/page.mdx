# Safety configuration

CallFlow places real phone calls — every run dials for real, from the first one. Every
guard here fails closed — meaning that if a guard cannot be evaluated, the call does
not go out.

## The guards

| Guard | Behaviour |
|---|---|
| Allowlist | While non-empty, only these E.164 numbers can be dialled. |
| Per-run ceiling | Hard cap on real calls in one run. Protects your balance. |
| Rate limit | Calls allowed per window. Paces a run to a human rhythm. |
| Daily budget | Shared daily ceiling across the whole organisation. |
| Calling window | Nothing is dialled outside it; contacts wait for the next opening. |
| E.164 validation | Malformed numbers are rejected before they reach the engine. |
| Suppression list | Permanent and global. Opt-outs are never dialled again, checked before every dial. |

All of them are visible as mono chips on the run composer, above the button that
starts the run. A guard that is off renders in flare with the word `OFF`, because an
unguarded configuration should look uncomfortable.

## The allowlist and the rate limit solve different problems

They are easy to confuse and they are not interchangeable.

**Use the allowlist while developing.** Put your own number on it and dialling anyone
else becomes impossible. This is the guard that protects strangers from your test
runs.

**Use the rate limit on a public deployment,** where visitors legitimately need to
call their own numbers but nobody should be able to drain the account or dial one
person repeatedly. This is the guard that protects your balance and your reputation.

Most teams want both.

## Calling windows

A window is a start time, an end time, and a timezone, set per campaign with an
organisation-wide default.

Outside the window nothing is dialled. Contacts are queued for the next opening rather
than counted as failures — which is the same reasoning behind treating a bad time as a
retry rather than an escalation.

## Environment configuration

For self-hosted deployments the guards are also settable as environment variables, and
the environment value acts as a ceiling the interface cannot exceed.

```bash
CALLFLOW_ALLOWLIST=+919876543210 # comma-separated E.164
CALLFLOW_MAX_CALLS_PER_RUN=3
CALLFLOW_RATE_LIMIT_CALLS=2      # per window
CALLFLOW_DAILY_BUDGET=25
```

Set `CALLFLOW_OWNER_KEY` and send it as an `X-CallFlow-Owner-Key` header to lift the
rate limits for your own testing. It does not lift the allowlist or the ceiling.

## Number masking

Phone numbers are masked — `+91*******210` — in every log, API response, and interface
surface. Revealing a full number is a separate, permissioned action.

Masking is implemented in exactly one place in the codebase, so a new screen cannot
ship without it by accident.

## While you are still setting up

Put your own number on the allowlist before your first run. While it's non-empty,
that's the only number a run can dial — the state you want to be in until you have
watched a real call go through end to end.
